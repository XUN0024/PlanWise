# 三模块队列、追问和候选明细修正

本次用户反馈包含三个不同问题，不能只归因于关键词或模型：

1. 笔记语义覆盖 `0/3`：当前没有有效笔记向量参与语义匹配。支出向量已经生成，不能证明笔记/任务也已经完成。
2. `machine learning 的话呢？` 没有查询资料：原路由只识别部分开头形式，漏掉句尾追问；回答又错误沿用了旧轮次的笔记数量。
3. `帮我列出我吃饭的开销` 取得了 8 条真实来源，但模型遗漏其中一条并虚构六月到八月的查询范围、宣称按日期降序却未排序。

用户导出的 jobs SQL 只包含 100 条支出记录（91 ready，9 pending 且保留 embedding_not_configured、attempts=0）。该文件只作数据分析，没有执行其中 SQL。它不是全表证明：之前完整状态已包含 note/task；索引表本来就统一保存三种类型，来源由 source_type 区分。

## 已实施

- `pw_search_claim` 对各模块的到期任务分别编号，再交错领取。保留每模块内部的到期顺序、SKIP LOCKED、过期租约恢复、generation/source hash 校验。每次领取数量和 Embedding 预算没有增加，不把未到重试时间的任务提前执行。
- 连续追问沿用前一轮实际路由的模块，但不沿用旧主题、日期或助手编造的事实。支持句尾“的话呢”“呢”和 What/How about；显式参考范围继续是上限，普通知识对话保持普通回答。
- 当前主题清理后重新生成查询向量和关键词。例如 AI 笔记之后追问 machine learning，仅检索新主题，不把 Artificial Intelligence 混入查询。
- 全部检索卡为空时，服务端生成覆盖说明。`0/3` 不再解释为必须精确拼写、不存在相关记录或缺少授权。无应用读取时，针对明显伪造的查询声明增加输出校验。
- 单模块支出“列出/列表/明细/list/show”请求，由服务端格式化全部真实候选。每条金额、日期、时间、付款方式和分类使用数据库事实；先取相关候选再按消费日期排序，明确这不是全库最新账单或完整总额。其他分析问题仍可调用模型解释。

“吃饭”等概念当前仍是语义候选，不自动宣称是完整 Food 分类。需要精确分类统计时使用现有明确分类/日期条件及 SQL 汇总，不统计候选页金额。

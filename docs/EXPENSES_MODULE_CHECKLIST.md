## 数据库部署步骤

1. 在 Supabase SQL Editor 执行 [预检查](../database/migrations/20261106_expenses_preflight.sql)。
   空结果表示未发现需要核对的记录；若有结果，先核对金额、分类、日期、描述与币种。
2. 执行 [增量迁移](../database/migrations/20261106_expenses_crud.sql) 全文。
   无需重建数据库或重跑 fresh_setup.sql。脚本可重跑，保留已有有效金额和创建时间。
3. 执行 [验证脚本](../database/migrations/20261106_expenses_verify.sql)。RLS 为 true，
   权限结果应为 `false / true / true / false / false`。
4. 本轮已完成基础 CRUD 迁移的项目，只需继续执行
   [支付方式/时间迁移](../database/migrations/20261107_expenses_payment_time.sql)。
   新脚本为增量修改，没有删除、重建或回填支出记录的语句。
5. 执行 [新字段验证脚本](../database/migrations/20261107_expenses_payment_time_verify.sql)。
   两列可空、无默认值；七项权限预期为 `false / true / true / true / true / false / false`。
6. 执行 [统计 RPC 迁移](../database/migrations/20261107_expenses_statistics.sql)。已部署前两轮的项目仅需执行这一份新迁移。
   不修改支出记录，不新增表或字段；新增只读、沿用 RLS 的统计函数。
7. 执行 [统计权限验证](../database/migrations/20261107_expenses_statistics_verify.sql)。
   五项预期为 `false / true / false / false / true`：匿名不可执行、登录可执行、不是 security definer、PUBLIC 不可执行、支出表 RLS 已启用。
8. 执行 [收据迁移](../database/migrations/20261107_expense_receipts.sql)。已完成前面部署的项目只需执行这份新迁移。
   脚本创建 expense_attachments、私有 expense-receipts bucket、权限与确认函数，不改动账单和 Notes 附件。
9. 执行 [收据验证](../database/migrations/20261107_expense_receipts_verify.sql)。bucket 应为 private、15728640 字节；最后四项权限为 `false / false / true / true`。
10. 刷新 Expenses 页面。无需修改 .env 或 OAuth。

迁移遇到旧负数、零、超精度/超范围金额、未知分类、空描述、异常日期或非 MYR 币种
会回滚，并报 EXPENSE_LEGACY_REVIEW_REQUIRED。先修正核对过的旧数据再重试；
脚本不会取绝对值、四舍五入、删除记录或编造描述。

currency 新增时旧记录按用户确认的 MYR 初始化。若旧记录实际使用其他币种，须先
人工核对原始账目。现有 currency 字段的非 MYR 记录不会自动换算或改写。

## 边界与持久化

- 记录字段：id、user_id、amount、currency、note（描述）、category、expense_date、payment_method、expense_time、created_at、updated_at。
- 前端服务只提交可编辑字段；数据库金额不使用浮点类型。
- 金额数据库不用 numeric(14,2) typmod，因为该类型会在 CHECK 前舍入超精度输入；
  numeric 与范围/精度约束提供等价的金额边界，并拒绝超过分的精度。
- 修改/删除匹配完整的原始 updated_at，保留微秒精度。创建重试只识别同 UUID 且内容
  完全一致的已提交记录，不覆盖已被其他窗口改过的记录。
- 成功写入后重新读列表。若随后读取失败，显示已保存/已删除通知和加载失败，
  重试仅重新读取，不重新提交写入。
- 草稿当前只在内存；失败后输入保留，刷新会有离开提示，不提供持久化离线草稿。
- 未来日期允许手动选择；本轮不实现收入、退款、多币种、汇率或自定义分类。

## 筛选与排序（2026-11-07 已实施）

### 查询口径

| 控件 | 规则 |
|---|---|
| 日期 | 全部、今天、近 7 天（今天及前 6 天）、本月（整月含未来日期）、自定义起止 |
| 自定义范围 | 两侧包含边界；允许单侧留空；开始不能晚于结束；以 expense_date 筛选 |
| 分类 | 全部或七种现有分类之一 |
| 支付方式 | 全部、六种现有方式、未记录（数据库 NULL） |
| 关键词 | 描述中不区分大小写的字面子串；去掉首尾空白；停止输入 300ms 查询 |
| 金额 | RM 上下界，两侧包含边界；允许 0 和单侧留空；最多两位小数，上下界不能颠倒 |
| 排序 | 日期/时间从新到旧或从旧到新，金额从高到低或从低到高，最近录入 |
| 重置 | 清除所有条件、回第一页、恢复默认日期/时间从新到旧排序 |

- 相对日期按用户设备本地日历解析，在一次查询中固定为明确起止日期，不作 UTC 日期平移。
- 金额查询提交规范十进制字符串，排序由数据库 numeric 执行。金额相同时再按支出日期/时间从新到旧、ID 从大到小。
- 日期/时间排序在每个日期内将 NULL 时间放最后；最终按 ID 从大到小补足相同值，避免分页时相同值顺序不定。
- 关键词使用转义后的 PostgREST imatch（PostgreSQL ~*），不会将用户输入的 `%`、`_`、`*` 或正则字符当作通配表达式。
  查询操作参考：[PostgREST 官方文档](https://docs.postgrest.org/en/stable/references/api/tables_views.html#operators)。
- 所有条件使用 AND 组合，数据库先筛选、排序，再返回当前页；不在当前页 25 条中做前端过滤。
- 调整条件与页码作为同一次状态更新，账号、页码与查询条件都参与列表结果匹配；取消旧搜索计时和忽略旧请求结果。
- 新增/编辑/删除成功后沿用当前条件重新查询；编辑后不再匹配的记录从列表消失，但仍显示保存成功通知。
- 筛选输入无效时保留控件值并提示错误，不请求数据库；无匹配与空账号分别显示；失败重试保留条件。
- 账号切换清空筛选输入和待执行搜索；写入进行中禁用筛选，沿用原有用户隔离及版本冲突处理。
- 此阶段无需新增 SQL、表或权限；数据库应已执行前两轮 CRUD 和支付方式/时间迁移。
- 筛选状态保留在当前页面内存；浏览器刷新或重新进入页面时恢复默认条件。

## 真实统计与图表（2026-11-07 已实施，线上部署待验收）

### 页面与统计范围

- 页面顺序为：标题与新增按钮 → 共用筛选 → 支出概览与图表 → 每页 25 条账单。
- 概览包括总额、笔数和平均每笔金额；分类金额/占比、支出趋势和支付方式金额/占比展示真实汇总。
- 日期、分类、支付方式、关键词和金额范围由同一份规范化条件生成，列表与统计都包含起止边界。
- 汇总统计全部匹配记录，不读取当前页进行加总；翻页和改变排序不会重新请求汇总。
- 新增/修改/删除成功后刷新列表和汇总；汇总读取失败单独显示重试，不能把已提交写入显示成保存失败。
- 修改筛选或账号时隐藏旧统计，取消旧请求结果；搜索继续沿用 300ms 防抖。

### 数据库与金额精度

- 新函数 public.get_expense_statistics 接受筛选条件及 auto/day/month 趋势粒度，不接受 user_id 参数。
- SECURITY INVOKER、空 search_path，按 auth.uid() 限定归属并沿用表 RLS；撤销 PUBLIC/anon 执行权限，仅 authenticated 可调用。
- 直接 RPC 调用也校验日期、金额范围/两位精度、分类、支付方式、搜索长度和趋势粒度。
- 一次 SQL 对全部匹配记录聚合总额、分类、支付方式和趋势，计算基于 expense_date，不使用 created_at 代替消费日期。
- 返回 JSON 中笔数和金额分均为十进制字符串；前端使用 BigInt 格式化和校验，不将累计金额转成 Number。
- 平均每笔金额保留到分，正数半分向上舍入；数据库用精确整数商实现，避免超大 numeric 中间除法先舍入。
- 返回数据校验各分组和趋势的金额/笔数合计、平均金额、日期及枚举；不完整数据提示失败，不能展示错误统计。

### 数据与删除顺序

- 独立私有 bucket：expense-receipts，文件大小限制 15728640 字节。
- public.expense_attachments 通过 expense_id 引用 public.expenses；元数据含归属、名称、类型、大小、路径及 pending/ready 状态。
- 路径为 user_id/expense_id/attachment_id/file，禁止覆盖；元数据 RLS/Storage restrictive fence 限定当前账号及所属支出。
- 完成 RPC 校验真实 Storage 对象存在且实际大小一致，客户端不可直接 UPDATE 或伪造 ready。
- Storage 插入对 pending 元数据加行锁，配合删除触发器防止上传与删除过程中元数据先消失。
- 单独删除收据：Storage API 删除文件 → 删除元数据。文件仍存在时，数据库拒绝直接删除元数据。
- 删除支出：先核对 updated_at → 清理所有收据文件和元数据 → 按原版本删除支出。
- 任一步失败保留支出供重试；Storage 与数据库之间不具备全有或全无事务，部分文件可能已经删除。并发新附件由外键 RESTRICT 阻止支出提前删除。
- Notes 的表、bucket、上传参数和默认 UI 仍按原配置使用；共享传输增加 bucket 参数，共享预览注入对应下载服务。
